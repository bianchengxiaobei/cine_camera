# C API Decision

Status: evaluated for 0.1; no stable C ABI in the initial release.

## Decision

CineRig 0.1 exposes a C++20 API only. A C API is not part of the initial
release. This is a deliberate scope decision, not an implementation omission.

## Rationale

- The public surface already uses C++ value types, standard containers, and
  virtual adapter interfaces. A C API would be a parallel API, not a thin
  wrapper, and would need its own lifetime and mutation rules.
- A stable C ABI requires frozen contracts for opaque handle ownership,
  allocation, error reporting, threading, callback reentrancy, and versioning.
  Freezing those contracts before the C++ API has shipped would add risk
  without a current consumer.
- The verified integration path is C++20: `find_package(CineRig)`, the
  `cinerig::cinerig` target, and host implementations of `IEntityWorld`,
  `ICameraOutput`, `IPhysicsWorld`, and the remaining adapter interfaces.
- There is no independent C host, engine plugin boundary, or language binding
  request that justifies the extra ABI surface today.

## Requirements If Added Later

A future C API should be designed as a complete boundary, not generated by
exposing C++ headers:

- Opaque handles for systems, cameras, brains, target groups, splines, and
  adapters; explicit create, destroy, and validity rules.
- `extern "C"` entry points with a versioned function table, so new functions
  can be added without changing existing struct layouts.
- No STL types in the ABI. Use caller-owned buffers, explicit lengths, and
  stable integer or string-view-like types.
- Explicit error codes and message retrieval, with no exceptions crossing the
  boundary.
- A documented allocator and ownership model, including who owns output
  snapshots and callback data.
- C and ABI tests in CI, plus a C++ convenience wrapper that remains thin.
- A compatibility policy that keeps the C ABI stable across the 0.x series or
  clearly marks it experimental.

## Revisit Criteria

Reconsider the C API when at least one of these is true:

- A non-C++ engine or tool needs to embed CineRig through a stable binary
  boundary.
- A language binding or plugin SDK has a concrete requirement and owner.
- The C++ API has remained stable through a release and its ownership model is
  no longer changing.
- CI can run dedicated C consumer and ABI compatibility tests.

## Current Integration

Use the installed CMake package:

```cmake
find_package(CineRig CONFIG REQUIRED)
target_link_libraries(my_target PRIVATE cinerig::cinerig)
```

The external smoke consumer built against the installed package is described in
[release-readiness.md](release-readiness.md). C++ examples live under
`examples/` and demonstrate the adapter interfaces.
